# 什么是分布式系统
把多台独立的计算机通过网络连接起来共同完成同一个任务。
分布式具有**高性能**、**高并发**和**高可用**的优点，但是引入的极大的复杂性，会导致**数据一致性**的问题

# 分布式和微服务的区别
分布式是一种**物理部署方式**，解决单台机器性能扛不住的问题。核心是**机器的拆分和协同**。

微服务是一种**软件架构设计思想**，主要解决系统代码堆积太多、难以维护的问题。核心是**业务逻辑和业务边界的拆分**。

微服务架构天然需要以分布式的方式进行部署

# CAP理论
分布式系统中**一致性**、**可用性**和**分区容错性**不可兼得。

当系统如果不能再时限内达成数据一致性，意味着分区现象的发生，需要再一致性和可用性之间做出选择。

# BASE理论
牺牲一致性，允许数据在短时间内不一致，以此换区系统的高可用和高性能。

- **Basically Available（基本可用）：**允许系统关闭一些功能，确保核心功能正常
- **Soft State（软状态）：**允许数据存在中间状态
- **Eventually Consistent（最终一致性）：**经过一段时间后，所有节点的数据会达成一致性

# 分布式锁的视线
- Redis分布式锁：
    - 需要以原子操作的方式实现读取、检查和设置锁变量
    - 锁变量需要设置过期时间
    - 锁变量的值需要区分不同客户端的加锁操作

- Zookeeper分布式锁：
    - 请求进来时在持久节点下面创新临时有序节点。
    - 判断创建节点是否是最小节点。是，获取锁。不是，阻塞进程，设置监听器监听节点。
    - 处理完业务逻辑后释放锁

# 什么时候需要分布式ID
分布式ID的目的是在多节点、多数据库环境下，如何生成一个**全局唯一**且最好是**有序**的标识

- 数据库分库分表
- 高并发的微服务多节点环境，并对数据库写入性能有极高要求
- 多系统打通合并数据，将多个系统的数据进行合并时用原来库里的自增ID会发生冲突

# 分布式ID方案
- UUID全球唯一，但无序、占用存储空间太大，不推荐
- 数据库号段模式，一次去请求数据库分配1000个ID，拿到本地内存慢慢分配。用完再去数据库请求1000个ID
- 基于Redis生成，速度快但成本开销大
- 雪花算法（主流），完全不需要依赖外部服务、在机器本地纯计算生成ID的算法。

# 什么情况下使用分布式事务
- 微服务架构下的跨服务协同
- 低层由于数据量大，做了分库分表。能绕开不用，就尽量不用

# 分布式事务的解决方案
- 两阶段提交协议（2PC）：**准备阶段**协调者向参与者发送准备请求，参与者执行事务并返回结果。**提交阶段**所有参与者就绪，协调者发送提交请求，参与者提交。
- 三阶段提交协议（3PC）：在2PC的基础上将准备阶段分为询问和准备阶段。询问阶段协调者询问参与者是否能执行事务，后续与2PC一致
- TCC：Try 阶段预留业务资源，Confirm 阶段确认资源完成业务操作，Cancel 阶段在失败时释放资源回滚操作。
- Saga：将长事务拆分为多个短事务，每个短事务有对应的补偿事务。某个短事务失败，按相反顺序执行补偿事务回滚系统状态。
- 可靠消息最终一致性方案：基于消息队列，业务系统执行本地事务时将业务操作封装成消息发至消息队列，下游系统消费消息并执行操作，失败则消息队列重试。
- 本地消息表：业务与消息存储在同一个数据库，利用本地事务保证一致性，后台任务轮询消息表，通过MQ通知下游服务，下游服务消费成功后确认消息，失败则重试。

# RPC的概念是什么？
允许程序调用运行在另一台计算机上的程序中的过程或函数

- 客户端调用：客户端程序调用本地的一个 「伪函数」，并传入所需的参数。
- 请求发送：客户端存根将调用信息（包括函数名、参数等）进行序列化，然后通过网络将请求发送到服务器端。
- 服务器接受和处理：服务器端接收到请求后，将请求信息进行反序列化，然后找到对应的函数并执行。
- 结果返回：服务器端将函数的执行结果进行序列化，通过网络发送回客户端。
- 客户端接受：接收到服务器返回的结果后，将其反序列化，并将结果返回给调用者。

# 常见限流算法
- 固定窗口限流算法：对一段固定时间窗口内的请求进行计数，如果请求数超过了阈值，则舍弃该请求
- 滑动窗口限流算法：将限流窗口内部切分成一些更小的时间片，然后在时间轴上滑动，每次滑动，滑过一个小时间片，就形成一个新的限流窗口。然后在这个滑动窗口内执行固定窗口算法即可。
- 漏桶限流算法
- 令牌桶算法

# 分布一致性算法
- Raft算法：把整个一致性过程拆成了三个很清晰的部分：选主、日志复制、安全性保证。
    - 选主：如果跟随者一段时间没有收到领导的信息就会变成候选人竞争领导
    - 日志复制：领导吧操作写成日志同步给所有跟随者，超过半数节点确认收到，领导者提交日志后告诉跟随者一起提交
    - 安全性：已经提交过的日志，永远不会被覆盖或丢失

- Paxos协议：多个节点协同，最终达成同一个决策
    - 准备阶段：提议者先给所有接受者发一个带有唯一编号的准备请求。接受者收到后，会判断如果没答应过比这个编号更大的提案，就回复同意，还会告诉提议者自己之前接受过的最大编号提案；要是已经答应过更大编号的，就直接拒绝。
    - 接受阶段：只有提议者收到超过半数接受者的同意，才能进入这一步 。
